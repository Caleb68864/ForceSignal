# Tactical map visuals and turn playback: findings, 2026-11-09

Branch `spike/pixi-map`. Scope: gather data, prove a PixiJS renderer can sit under the existing
React map, and build the tests that later roadmap items are measured by. Not the full feature.

Everything below was measured or observed, not read off types. The data source is
`tests/ForceSignal.Application.Tests/PlaybackFixtureCapture.cs`. It plays one busy turn through the
real `InMemoryMatchService` with the invented test rules and seeded dice, then writes six snapshots
to `src/ForceSignal.Web/src/lib/playback/fixtures/`. The turn includes a multi-leg helm, a hull
stopped by the table edge, a ship with no order, a ship wrecked after its order was revealed, a
fighter flight met by point defence, a salvo, every weapon kind, a threshold check that knocks out
a weapon, and a kill. Regenerate with:

```
FORCESIGNAL_WRITE_PLAYBACK_FIXTURES=$PWD/src/ForceSignal.Web/src/lib/playback/fixtures \
  dotnet test tests/ForceSignal.Application.Tests --filter PlaybackFixtureCapture
```

I chose a fixture capture over `scripts/two-player-smoke.py` because the smoke script needs Python
Playwright, which isn't installed. The capture also goes through the same service code the API
calls, but it is repeatable and covers more cases. Wire shape: the capture serialises with the API's
own options (web defaults plus string enums, `Program.cs:51-53`).

## A1. What playback needs vs what the snapshot has

### Movement

| Need | Snapshot has it? | Evidence |
|---|---|---|
| Every moved ship has its path | **No.** A ship with no order drifts its full velocity but has no `MovementResult`. | The Drifter moved 10,10 → 10,14 (log seq 47); `movementResults` has 6 entries for 7 moving ships. `InMemoryMatchService.cs:1645-1657` moves drifters outside the commitment loop. |
| Segments in order, enough points to animate | **Yes.** `segments` are ordered legs (course + distance), one per helm change. Walking them gives every corner, and nothing curves between corners. | The Lance's `[3:1.5, 4:3, 3:1.5]` reproduces "helm S1, P1". |
| Where the move started | **No.** There is no start position. The client walks the segments backwards from the current position (`mapGeometry.ts` `trailPointsForResult`). | |
| Correct start when the table edge stopped the ship | **No: wrong today.** The server clamps each step at the edge (`InMemoryMatchService.Combat.cs:604-625`) but reports the unclamped distance. | The Edge Runner started at 66,8 and flew 8 on course 3. The server stopped it at 72. Walking back puts the start at 64. The DOM trail overlay draws this wrong line today. |
| Only ships that actually moved | **No.** A ship destroyed before movement keeps its commitment's `Result`, so it gets a `MovementResult` for a move it never made. | The Wreck (log seq 46: "order was discarded") has a 4-unit result and the trail overlay draws one. From the client it looks the same as the Picket, which moved and was then destroyed in firing. |
| Fighter flights | **No.** `MoveFighterGroup` changes position and logs a sentence. There's no result and no start point. | Hawk Flight 28,30 → 38,26 (seq 23), only in the log. |
| Ordnance motion | **No.** Markers advance at the end of firing (`AdvanceOrdnanceMarkers`, `InMemoryMatchService.cs:2032`) with no previous position. | |
| Results visible at the right time | **Partly.** During the Movement phase, results are already on the snapshot but ships haven't moved yet, so walking back from there is wrong. | Fixture 02 has 6 results with ships at their start positions. `buildTurnTimeline` returns `awaiting-movement` for this case. |
| Replay after the turn advances | **No.** Advancing clears `Commitments` and `FiringResults` (`InMemoryMatchService.cs:1600-1602`). | Fixture 06: no results. "Replay last turn" is impossible today. |

Rounding: the server rounds each step to 0.001. The client's backward walk doesn't, so the Lance's
start reads 17.99992 instead of 18. That's harmless on screen, but it's the same root cause as M1.

### Ordnance markers

Markers have position, course, speed, endurance and status. There's no history and no link to
damage. A salvo is resolved at the end of movement, before firing opens. In the bench screenshot
its marker sits on the target, but nothing on the snapshot can play its strike.

## A2. Decision: we need an ordered server-side event list

The timeline cannot be derived from the existing fields without parsing English log sentences:

1. **Four outcome kinds are log-only**: salvo strikes, point defence, threshold system losses, and
   needle system kills. Fighter strikes stopped by point defence have no record at all.
2. **Movement has three wrong or missing cases** (edge clamp, drift, discarded order) and fighters
   have none. All of them need the start point, which only the server knows.
3. **Ordering across kinds is lost.** A salvo strikes between movement and firing. Point defence
   fires before the strike it meets. Thresholds roll when a volley closes. `firingResults` order is
   correct among shots, but nothing places a threshold or a PD roll between them except the log's
   `sequence`, and a result can't be tied to its log line.
4. **A turn disappears when it ends.** No replay of last turn, and no catch-up for a device that
   reconnects after the turn advanced.

Proposal: `MatchSnapshot.turnEvents: TurnEventDto[]` for the current turn, plus `lastTurnEvents`
for the previous one. It's written at the same points `AddLog` is called today, and shares the
log's sequence counter so every event has its sentence:

```
TurnEventDto(long Sequence, int TurnNumber, string Kind, Guid? ActorId, Guid? TargetId, ...payload)
  ShipMoved        { startX, startY, segments, endX, endY, clamped }   // ordered AND drifting ships
  OrderDiscarded   { shipId }                                          // wrecked before moving
  FighterFlew      { fromX, fromY, toX, toY }
  SalvoStruck      { markerId, launched, arriving, pdRolls, pdKills, damage, armorApplied, hullApplied }
  SalvoWasted      { markerId }
  PointDefenseFired{ defenderId, groupId, rolls, kills }
  WeaponFired      { firingResultIndex }                               // FiringResult stays the record
  ThresholdChecked { targetId, row, rolls, lostSystems[] }
  ShipDestroyed    { shipId, causeSequence }
  OrdnanceMoved    { markerId, fromX, fromY, toX, toY, expired }
```

`buildTurnTimeline` keeps its signature. It reads `turnEvents` when present and falls back to
today's derivation otherwise. The four `it.fails` cases in `timeline.test.ts` flip to `it` as each
event lands. That flip is the acceptance test.

## A3. The current DOM map, measured

Method: `e2e/measureMap.mjs` against `bench/map.html` (production build with React's profiling
renderer so `<Profiler>` reports; both renderers pay that equally). The bench renders the real
`PlayMap` against the captured turn at N hulls. Median of 3 runs. Desktop is 1440×900 at DPR 1.
"Mobile" is 390×844 at DPR 3 with touch and the **CPU throttled 4×** through CDP. The GPU is
not throttled, so this is a slow phone CPU paired with a desktop GPU. Pan/zoom is 40 scripted
drag steps then 10 wheel notches. Frame stats come from `requestAnimationFrame` deltas.
Machine: Linux, Chromium 156, Radeon RX 470 (Vulkan, `--enable-gpu --use-angle=vulkan`).

**Bundle (production `npm run build`, before the spike):** one JS chunk, 479.7 kB raw /
**133.9 kB gzip**, CSS 41.2 kB / 8.7 kB gzip.

Reading it:
- The DOM map holds 60 fps on desktop up to 30 ships and dips at 60 (55.5 fps, p95 33 ms).
- On the throttled phone, pan smoothness falls with N (57 → 53 → 46 fps; 4 frames over 50 ms at
  60 ships).
- **The cost is React, not paint.** Every pointer move sets viewport state, and PlayMap re-renders
  every ship button. Commit time during the pan grows with N (desktop 28 → 61 ms total; phone

- Paint and memory are cheap: first paint 145–183 ms desktop and 0.5–0.63 s on the phone, heap
  4.6–8.1 MB. DOM nodes grow by about 19 per ship.


## A4. The PixiJS spike, measured

Same harness, `?renderer=pixi`. Pinned **`pixi.js@8.22.0`** (MIT, published 2026-10-01).

**Bundle:** the main chunk goes from 479.7 → 481.4 kB raw, **133.9 → 134.9 kB gzip (+1.0 kB)**,

Reading it:
- **Playback is smooth where it matters.** On a real GPU, playback holds 60 fps with zero slow
  frames at 10, 30 and 60 ships, on desktop and on the throttled phone.
- **Panning matches or beats the DOM map** (phone, 60 ships: 49 vs 46 fps). The remaining pan cost
  is the same React commit as the DOM map, because the DOM buttons are still there.
- **Time to first map paint costs** about +120 ms on desktop (262–313 ms) and about +400 ms on the
  throttled phone (0.86–1.06 s). That's the chunk download, parse and WebGL init. It's paid once
  per load, so preloading the chunk when a match opens would hide most of it.
- **Memory:** heap +5–17 MB over the DOM map (9.6–23.7 MB). GPU memory isn't visible to these
  counters. The canvas is one layer at up to DPR 2.
- **Software WebGL is the weak case.** At 60 ships, playback drops to 38–40 fps and pans to
  32 fps. That's the case for keeping the DOM map as the fallback (roadmap item 6).
- **Fix found by measuring.** The first build redrew all geometry twice on every pan event. On
  SwiftShader at 60 ships, desktop pans ran at 30.3 fps with 14 slow frames
  (`measurements/measure-v1.json`). Pans now only move the world and re-render, and only a zoom change rebuilds
  geometry, giving 32.7 fps and 7 slow frames. The DOM map's 60 fps on desktop SwiftShader shows the
  remaining gap is software rasterisation, not the scene.


## Coordinates

The Pixi layer uses `viewTransform.ts`, which is the DOM's own rule: `mapPercent` of the content
box, then `translate(x,y) scale(s)` from `0 0`. Markers are counter-scaled by `1/scale`.
`viewTransform.test.tsx` checks a real Pixi `Container` against that rule for 63 grid points at
four zoom/pan states. It also renders the real `PlayMap`, drives it with the keys a player uses,
and reads each ship button's `left`/`top` back, then round-trips through `tablePointFromClient`. In
the browser, DOM labels sit exactly on the Pixi hulls (bench screenshot).

There's one pre-existing DOM inconsistency, and it isn't caused by Pixi: `tablePointFromClient`
measures with `getBoundingClientRect()` of `.table-map`, which includes its 1 px border, but markers
are placed in the content box. At scale 1 a tap lands ≤ 1 px + 0.3 % off. That's invisible, but the
parity test documents it with a content-box rect.

## What the spike is

`?renderer=pixi` on the real app (or `bench/map.html?renderer=pixi&ships=N`):

- Pixi canvas under the DOM content (`components/map/pixi/`), loaded as its own chunk.
  Layers: seeded starfield, resolved trails, hulls (procedural arrowheads in fleet colour, constant
  screen size), FX.
- The DOM keeps everything interactive: ship buttons (now see-through, so taps, focus, the context
  menu and screen readers are unchanged), inspector, ruler, arcs, fighter rings and ordnance
  markers.
- Playback: moves fly together, then each shot plays alone in server order. New shots autoplay as
  they arrive, so a device that skipped snapshots still plays every shot. The bar has Skip,
  Replay, an Effects toggle (stored per device) and a live caption with every number taken from the
  server's record ("Lance → Picket · Battery A · 0 armour, 1 hull · destroyed").
- FX by registry: beam (glow line, muzzle flare, fade), pulse torpedo (projectile with trail),
  needle (flickering thin line), fighter strike (curving swarm), unknown (flash). Impacts are read
  off the result: shield shimmer when `screenReduction > 0`, sparks when armour or hull was
  applied, an explosion on the attributed kill, and a puff on a miss. All of these are original
  procedural drawing, so there is nothing to add to ATTRIBUTION.md. Pixi itself is MIT (npm
  package; licence ships in `node_modules/pixi.js/LICENSE`).
- Reduced motion (OS preference or Effects off): no animation, the result appears at once, and
  Replay is disabled.
- The canvas renders on demand (ticker stopped), so an idle table costs no frames.

Not done (spike): the canvas doesn't draw arcs or the ruler (they stay DOM SVG), ordnance markers
don't animate, and there's no text in the canvas.

## Roadmap

Each item is done when its test says so. Items 1–5 are server-side and unblock the rest. None of
them needs Pixi.

1. **Movement start points.** Add `startX/startY` to `MovementResult` (and `clamped`). The timeline
   reads them instead of walking back.
   *Test:* `timeline.test.ts` "starts a hull the table edge stopped where it really started"
   flips from `it.fails` to `it`. The DOM trail overlay is fixed by the same field (add a
   `trailPointsForResult` case for a clamped result).
2. **Every mover has a record.** Drifting ships get a `MovementResult` (or a `ShipMoved` event), and
   a ship wrecked before movement has its result dropped or flagged.
   *Test:* the "flies a ship that held course" and "does not fly a ship whose order was discarded"
   cases flip to `it`. Add an Application test asserting `movementResults` covers exactly the ships
   whose position changed in `AdvanceTurn`.
3. **Ordered `turnEvents` on the snapshot** (shape in A2), sharing the log sequence.
   *Test:* new C# test: for the fixture turn, every `AddLog` category in {Movement, Fighters,
   Ordnance, PointDefense, Threshold, Fire} has exactly one event with the same sequence. The
   salvo `it.fails` flips. The fixture capture is regenerated and `timeline.test.ts` gains salvo,
   PD, threshold and fighter-flight cases.
4. **Keep last turn's events** (`lastTurnEvents`) through `AdvanceTurn` and persistence.
   *Test:* the "says a past turn is unavailable" case becomes "replays the previous turn". A
   persistence round-trip test keeps it across restart.
5. **Contract drift.** Add `mapRange`, `rangeDisagreed`, the six ship fields and nullable `faction` to
   `types.ts`.
   *Test:* a vitest that checks every key in fixture 05's objects is declared on the matching TS
   type (keys read from the fixture, declared keys from a typed sample object).
6. **Adopt the canvas layer behind a setting, not a URL.** Move `?renderer=pixi` to a per-device
   setting and keep the DOM map as the fallback when WebGL fails to initialise.
   *Test:* `e2e/pixiMap.spec.ts` plus a new case that forces `init` to reject and asserts the DOM
   hulls are visible. Coordinate parity (`viewTransform.test.tsx`) stays green.
7. **Pan cost with many ships.** PlayMap re-renders every ship button on every pointer move (React
   commits during a pan grow with N: see A3). Move the viewport transform to a ref and style write,
   or memoise the marker list.
   *Test:* `measureMap.mjs` desktop 60 ships, React commit time during the scripted pan
   ≤ 25 % of today's, and mobile pan p95 frame ≤ 20 ms.
8. **FX for the new events** (salvo volley with PD interceptions, point-defence tracers, threshold
   flare, explosion on `ShipDestroyed` from any cause), all through the registry.
   *Test:* the registry guard is extended to event kinds the same way it covers `WeaponKind`, and
   `noOutcome.test.ts` stays green.
9. **Playback reads like a story.** A caption per event (already for shots) and per new event kind,
   with every number taken from the event.
   *Test:* a vitest that, for each fixture event, the caption contains every applied-damage number
   on the record and no number that isn't on it.
10. **Performance budget.** Keep the Pixi chunk ≤ 160 kB gzip and the main chunk growth ≤ 2 kB.
    *Test:* a size check in `npm test` (or CI) over `dist/` after `npm run build`.
