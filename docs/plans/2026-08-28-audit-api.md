Scope: read-only audit of `ForceSignal.Api`, `ForceSignal.Application` (Matches + Ground), `ForceSignal.Infrastructure.Persistence`, contracts, config, Dockerfile.

## 1. How the API is put together (orientation for an implementer)

**Route registration.** Everything is minimal APIs — no controllers, no MVC.

- Full Thrust routes are declared inline in `src/ForceSignal.Api/Program.cs:238-761`.
- The two ground engines live in extension methods in `src/ForceSignal.Api/Endpoints/GroundCombatEndpoints.cs` (`MapStarGruntEndpoints`, `MapDirtsideEndpoints`), mapped only when the matching flag is on (`Program.cs:228-236`). Both flags default to `false` (`FeatureFlags.cs:35-38, 63-68`), so a disabled engine contributes no routes at all and its paths 404.
- Middleware order (`Program.cs:146-197`): OpenAPI/Scalar (Development only) → exception-mapping middleware → security-headers middleware → `UseCors()` → `UseRateLimiter()` → endpoints. There is no authentication or authorization middleware anywhere in the solution (grep-verified: no `AddAuthentication`, no `RequireAuthorization`).

**Error model.** There is no exception filter and no `AddProblemDetails`. A single terminal middleware at `Program.cs:152-183` catches exactly seven exception types:

```
UnauthorizedAccessException, InvalidOperationException, ArgumentException,
KeyNotFoundException, JsonException, FormatException, OverflowException
```

and maps them:

| Exception | Status |
|---|---|
| `UnauthorizedAccessException` | 403 "Action not allowed" |
| `InvalidOperationException` whose `Message` contains "not found" (case-insensitive) | 404 |
| everything else in the list | 400 |

Anything *outside* the list — `NullReferenceException`, `SqliteException`, `IndexOutOfRangeException` — escapes to the host as a 500. `ex.Message` is written into the ProblemDetails `detail` field **in every environment** (`WriteProblem`, `Program.cs:784-788`).

So the convention a service follows is: throw `InvalidOperationException` with player-readable text for a refusal, `UnauthorizedAccessException` for a permission failure, and include the literal words "not found" when you want a 404. Note this makes the 404 mapping stringly-typed and fragile.

**Token validation.** Participant tokens are 64 hex chars from `RandomNumberGenerator.GetBytes(32)` (`InMemoryMatchService.State.cs:195`). There are two entry paths:

1. `ReadParticipantToken(HttpRequest)` (`Program.cs:765-779`) reads the `X-Participant-Token` header — used by only three routes (snapshot, ready, advance-turn). Blank/whitespace header throws `UnauthorizedAccessException`.
2. Every other authenticated route carries `ParticipantToken` as a field on the request body record.

Both converge on `FindParticipant(MatchState, string)` (`InMemoryMatchService.cs:1632-1636`), which rejects blank tokens and then matches against claimed participants using `TokensMatch` → `CryptographicOperations.FixedTimeEquals` (`:1644-1647`).

Ownership is then re-checked per entity:
- `FindOwnedShip` (`:1649-1659`) — resolves the ship, walks to its fleet, compares `OwnerParticipantId`.
- `FindOwnedOrdnanceMarker` (`:1661-1671`) — compares `marker.OwnerParticipantId`.
- Owner-only actions compare `participant.Role != "Owner"` inline (table, rules profile, points limit, advance turn).

The restore/claim flow has no token yet — that is what it exists to issue — so the **room code** stands in via `RequireJoinCode` (`Restore.cs:406-412`).

**Entity lookup.** Ships, fleets and markers are addressed by their own id without a match id, so the service keeps `_shipToMatch`, `_fleetToMatch`, `_markerToMatch` indexes (`InMemoryMatchService.cs:146-148`), resolved through `FindMatchByEntity` (`:1608-1611`).

**Concurrency.** `InMemoryMatchService` serializes everything on a single `Lock _gate` (`:138`). Every public method takes it; the id indexes are only mutated inside it. Persistence is called through `MatchState.Touch` → `Persist` (`State.cs:91-95`), so every mutation writes to SQLite **inside** the lock — deliberate, documented at `SqliteMatchStore.cs:19-25`. SignalR broadcasts happen *after* the service call returns, outside the lock, both in `Program.cs:781-782` and `MatchHub.NotifyPresence`. I found nothing mutated outside the lock and no broadcast inside one.

The two ground services follow the same shape independently (their own `Lock _gate`, their own dictionary, save-inside-lock).

**Resource ceilings (Full Thrust only).** `InMemoryMatchService.cs:183-213` defines `MaxParticipantsPerMatch=16`, `MaxFleetsPerMatch=32`, `MaxShipsPerMatch=400`, `MaxWeaponsPerShip=40`, `MaxOrdnanceMarkersPerMatch=400`, `MaxFiringResultsPerMatch=5000`, `MaxLogEntriesPerMatch=4000`, `MaxRepairJobs=32`, `MaxDisplayTextLength=120`, `IdleMatchRetention=24h`, `MaxConcurrentMatches=500`. Enforced by `RequireRoom` (`:216`) on live mutation and `RequireWithin` (`:225`) on restore. **The ground engines have no equivalent of any of this.**

## 2. Findings

### HIGH

#### H1. Unauthenticated, unrate-limited match creation destroys live games
**File:** `Program.cs:238-244`, `InMemoryMatchService.cs:237, 1553-1569, 1571-1597`
`POST /api/matches` carries no `RequireRateLimiting` policy. `CreateMatch` calls `EvictIdleMatches`, which at `:1564` runs `while (_matches.Count >= MaxConcurrentMatches)` and evicts the match with the oldest `LastActivity`. `Forget` (`:1571`) additionally calls `_store.Remove(matchId)`, deleting the row from SQLite — so the eviction is permanent, not just an in-memory drop.

500 unauthenticated POSTs evict every game in progress. A real table idle for two minutes while players argue about a range measurement has an older `LastActivity` than a freshly created attacker match, so genuine games go first.

**Severity:** high (availability + data destruction, no credentials needed)
**Fix:** add a per-IP fixed-window limiter to `POST /api/matches`, and at the ceiling refuse (`RequireRoom`-style) rather than evict any match whose `LastActivity` is inside the retention window.

#### H2. Every ground-combat route is completely unauthenticated
**File:** `GroundCombatEndpoints.cs:26-399` (all 20 StarGrunt + 13 Dirtside routes)
Every route takes only a `gameId` and acts. There is no participant token, no session concept, and no binding between a caller and a `SideId`: any client holding a game id can activate, fire, pass, and end turns **for either side**, and `GET /api/{engine}/games/{gameId}` discloses the entire game state to anyone with the id. None of these routes is rate-limited either.

The game id is a v4 GUID so it is not guessable, but it is a bearer capability with no revocation, no scoping, and it appears in URLs (proxy logs, browser history, `Referer`).

**Severity:** high (complete absence of an authorization model on a mutating surface)
**Fix:** mint a participant token in `CreateGame`, bind each token to a `SideId`, require it on every mutating ground route, and check side ownership in `BeginActivation`/`Fire`/`Pass`. Mirror `FindParticipant`/`TokensMatch` from the match service so the two agree.

#### H3. `SettleTheDowned` loops an unbounded caller-supplied count while holding the global lock
**File:** `src/ForceSignal.Modules.StarGrunt/Game/StarGruntGame.Assault.cs:274`, reached from `StarGruntGameService.cs:330-343`, contract `StarGruntContracts.cs:164-169`
```csharp
for (var figure = 0; figure < downed; figure++)
{
    switch (CloseAssault.Fate(dice.Roll(QualityDie.D6), deadUpTo, woundedUpTo))
```
`downed` comes straight off `StarGruntSettleDownedRequest.Downed` with no upper bound — the only guard is `downed <= 0` at `:265`. `downed = 2147483647` rolls two billion dice inside `Command`'s `lock (_gate)` (`StarGruntGameService.cs:358-366`), wedging the entire StarGrunt engine for hours from one small unauthenticated request. There is no cancellation token threaded through, so aborting the HTTP connection does not stop it.

**Severity:** high (single-request denial of service against the whole engine)
**Fix:** clamp `downed` to the unit's living figure count, or a hard ceiling, before the loop.

#### H4. Ground games are never capped, never evicted, and never expire
**File:** `DirtsideGameService.cs:88, 118-131`; `StarGruntGameService.cs:151-161`
`private readonly Dictionary<Guid, Held> _games` is a plain dictionary. There is no `MaxConcurrentGames`, no idle-retention window, no eviction pass, and no `Remove` path at all — a created game lives for the life of the process and its SQLite row lives forever. `CreateGame` is unauthenticated and unrate-limited, and writes a row on every call.

**Severity:** high when a flag is on (unbounded memory and unbounded disk from anonymous requests)
**Fix:** port the `MaxConcurrentMatches` / `IdleMatchRetention` / `EvictIdleMatches` discipline from `InMemoryMatchService.cs:204-213, 1553-1597` into both ground services.

### MEDIUM

#### M1. Rate limiting collapses to one global bucket behind a reverse proxy
**File:** `Program.cs:114-121, 125-132`
Both policies partition on `context.Connection.RemoteIpAddress?.ToString() ?? "unknown"`. There is no `UseForwardedHeaders` anywhere in the solution (grep-verified). Behind any reverse proxy, container ingress, or load balancer, every caller shares the proxy's address: the room-code limiter becomes a **global** 20 requests/minute and restore a global 10/minute. One player retrying a mistyped code locks out the whole table, while an attacker on the same side of the proxy is unaffected. It also means the protection intended by H1's fix would be similarly defeated.

**Severity:** medium (turns a defensive control into a self-inflicted denial of service)
**Fix:** `builder.Services.Configure<ForwardedHeadersOptions>(...)` with explicit `KnownProxies`/`KnownNetworks`, and `app.UseForwardedHeaders()` placed **before** `UseRateLimiter()`.

#### M2. Room code entropy is 15 bits
**File:** `InMemoryMatchService.cs:1679-1685` (word list), `:1694-1720` (`CreateJoinCode`)
32 words in 3 slots = 32,768 codes. The code alone authorises: joining a match (`Program.cs:246`), resolving it to a match id (`:316`), listing its seats (`:328`), and **claiming a seat, including the owner's** (`:338`). At 20 tries/minute the space is walked in ~27 hours from one IP, and in minutes from a modest set of IPs — and per M1 the per-IP partition may not hold at all.

Compounding this: `POST /api/matches/{matchId}/seats/{participantId}/claim` (`Program.cs:338-354`) is the **only** room-code-authenticated route with no `RequireRateLimiting` at all.

**Severity:** medium
**Fix:** add a fourth word slot (20 bits) or always append the numeric suffix currently used only as a collision fallback (`:1712`), and apply `RoomCodeLookupPolicy` to the claim route.

#### M3. Ship, class and weapon names bypass truncation on the update paths
**File:** `InMemoryMatchService.cs:541-542`, `:584`, `Normalization.cs:202`
```csharp
ship.Name = string.IsNullOrWhiteSpace(request.Name) ? ship.Name : request.Name.Trim();
ship.ClassName = string.IsNullOrWhiteSpace(request.ClassName) ? null : request.ClassName.Trim();
```
No `Truncate`. Same at `:584` in `DuplicateShip` (`request.Name.Trim()`) and `Normalization.cs:202` (`w.Name.Trim()` inside `NormalizeWeapons`). Every other display string goes through `NormalizeText` → `Truncate` at `MaxDisplayTextLength = 120` (`Normalization.cs:130-136`).

No global `MaxRequestBodySize` is configured (grep-verified), so Kestrel's 30MB default applies. A 30MB ship name is stored, replayed into `DescribeShip` (`Snapshot.cs:133-139`) on every log line it appears in, and re-serialized into every snapshot broadcast to every device at the table. With 40 mounts/ship and 400 ships/match the amplification is severe.

**Severity:** medium
**Fix:** route those three assignments through `NormalizeText`/`Truncate`.

#### M4. Restored battle-log entries are not normalized
**File:** `Restore.cs:188-197`
```csharp
match.AddRestoredLog(new MatchLogEntryState(
    entry.Sequence, entry.Timestamp, entry.TurnNumber,
    entry.Phase, entry.Category, entry.Message));
```
`Phase`, `Category` and `Message` are copied verbatim from the uploaded snapshot. The entry *count* is capped at 4000 (`:42`) but each string is unbounded up to the 8MB restore body limit. Each restore creates a match retained for 24h, cap 500 → roughly 4GB upper bound, reachable at 10 restores/min/IP. Every other restored string in this file goes through `NormalizeText`.

**Severity:** medium
**Fix:** `NormalizeText` each of the three fields, matching the ship/fleet path.

#### M5. `RestoreAll` / `LoadPersistedMatches` catch too narrow an exception — one bad row breaks startup
**File:** `Persistence.cs:56-81` (Full Thrust), `DirtsideGameService.cs:99-115` and equivalent in `StarGruntGameService.cs:139` (ground)

*Full Thrust — worst case:* `LoadPersistedMatches` catches only `JsonException` (`:65`). A record that parses but has an empty `Participants` array reaches `FromPersisted` (`:132`), which does `new MatchState(..., seats[0])` at `:137` → **`IndexOutOfRangeException`**. This runs inside the singleton constructor (`InMemoryMatchService(rollDie, store, loadPersisted: true)`, wired at `Program.cs:74-75`), so the whole API fails to start. Null `Fleets`/`Ships`/`OrdnanceMarkers`/`MatchLog` produce `NullReferenceException` at `:189-226` with the same effect.

*Ground:* `RestoreAll` catches only `ArgumentException`. `DirtsideGameSerialization.Restore` converts `JsonException` into `ArgumentException` (`DirtsideGameSerialization.cs:95-97`), so ordinary garbage is handled — but a row that parses with a null/default `Units` array reaches `read.Units.ToImmutableDictionary(unit => unit.Id)` (`:68`) and throws `InvalidOperationException` from a default `ImmutableArray`, escaping to the DI factory and 500-ing every ground route for the process lifetime.

The comment at `Persistence.cs:52-55` states the intent ("One unreadable match should cost that match, not every other game on the machine") — the catch is simply too narrow to deliver it.

**Severity:** medium (startup denial of service from a single corrupt row; requires DB write access or a crash mid-write)
**Fix:** widen both catches to `Exception` (log and `continue`), and guard `persisted.Participants` for null/empty before `seats[0]`.

#### M6. Null nested objects in request bodies produce 500s
**File:** `MatchContracts.cs:214, 221, 238`; `InMemoryMatchService.cs:1336`; `Preview.cs:47`; `FullThrustLightCinematicRules.cs:106`
`MovementOrder Order` is a non-nullable record parameter on `CommitOrderRequest`, `RevealOrderRequest` and `PreviewOrderRequest`, but System.Text.Json will happily bind `"order": null`. It then reaches `_rules.Validate(shipState, thrust, request.Order)` where `order.VelocityDelta` throws **`NullReferenceException`** — not in the middleware's catch list, so a 500.

This is the general shape of the gap: the middleware handles seven exception types and nothing guarantees a handler only produces those. Other nullable-nested fields are handled defensively (`request.Rules ?? RulesProfile.Empty` at `:390`, `request.Jobs ?? []` at `:798`, `request.Weapons` via `NormalizeWeapons`), so this is an inconsistency rather than a systemic omission.

**Severity:** medium (500s on a trivially-reachable input; a 400 is the correct answer)
**Fix:** null-check `request.Order` in the three handlers, and add `NullReferenceException`/`ArgumentNullException` to the middleware mapping as a backstop.

#### M7. `/ready` discloses deployment configuration and can never report not-ready
**File:** `Program.cs:204-217`, `ReadDeploymentWarnings` `:826-868`, `Dockerfile:13`
Unauthenticated, `/ready` returns `environment` (the environment name), `cors` mode, `persistence` mode, the full `features` DTO, and free-text `warnings` describing exactly which subsystems are unfinished or unconfigured. It also always returns 200 — including when the warnings say state is in-memory and will be lost — so the Dockerfile `HEALTHCHECK` on it can never detect an unready container.

**Severity:** medium (information disclosure + a health check that cannot fail)
**Fix:** split a bare liveness `/ready` (200/503, no body detail) from a diagnostics endpoint that is authenticated or bound to loopback.

### LOW

#### L1. No collection or string caps anywhere in the ground engines
**File:** `StarGruntContracts.cs:64-65, 155, 198`; `DirtsideGameService.cs:272, 287, 338`; `StarGruntGameService.cs:397-405, 409`
`AddStarGruntUnitRequest.Figures` and `.Weapons`, `StarGruntMeleeRequest.Pairings`, `StarGruntFireRequest.SupportWeapons`, and Dirtside's `Elements`/`Weapons` all take whatever arrives, bounded only by Kestrel's 30MB default. Unit/element/weapon ids and names go through `Required(...)` which trims but never truncates (`DirtsideGameService.cs:338`, `StarGruntGameService.cs:409`). Units per game are uncapped. Compare `MaxShipsPerMatch`/`MaxWeaponsPerShip`/`Truncate` on the Full Thrust side.

#### L2. Ground game logs grow forever and are re-serialized on every action
**File:** `src/ForceSignal.Modules.Dirtside/Game/DirtsideGame.cs:57, 101`
```csharp
public ImmutableArray<string> Log { get; init; } = [];
public DirtsideGame WithLog(string entry) => this with { Log = Log.Add(entry) };
```
No equivalent of `MaxLogEntriesPerMatch` / `TrimLog` (`State.cs:127-138`). The whole log ships in every snapshot (`DirtsideGameService.cs:369`) and the whole game is rewritten to SQLite on every command (`:259`), so a long game is O(n²) in both CPU and disk writes. StarGrunt has the same shape.

#### L3. No SQLite `busy_timeout`; the retry blocks the global lock
**File:** `SqliteMatchStore.cs:67-68`; three instances over one file at `Program.cs:72, 86, 95`
`PRAGMA journal_mode=WAL` and `synchronous=NORMAL` are set; `busy_timeout` is not. Three separate `SqliteMatchStore` instances open the **same database file** on separate connections (different tables, so no data mixing — the comment at `DirtsideGameService.cs:96-98` about "every kind of game side by side" is stale). WAL permits one writer at a time.

`Microsoft.Data.Sqlite` retries on `SQLITE_BUSY` up to its 30s default command timeout, so this rarely fails outright — but that retry happens inside `_gate`, so a contended write stalls the entire match service for up to 30 seconds. A write that does eventually fail throws `SqliteException`, which is **not** in the middleware's catch list, so it 500s *after* the in-memory state has already been mutated: memory and disk diverge silently and the next restart loses the turn.

**Fix:** `Execute("PRAGMA busy_timeout=5000;")` alongside the other pragmas, and map `SqliteException` explicitly (503 or 500 with a stable message).

#### L4. No HTTPS redirection, HSTS, or host filtering
No `UseHttpsRedirection`, `UseHsts` anywhere (grep-verified); `appsettings.json` sets `"AllowedHosts": "*"`. Defensible for the stated laptop-at-a-table deployment, but the security-header middleware at `Program.cs:185-194` implies a hardening posture that this omits. Worth an explicit note in deployment docs rather than silence.

#### L5. `ClaimSeatRequest.DisplayName` is accepted and silently ignored
**File:** `Restore.cs:413-439`, contract `MatchContracts.cs:589`
`ClaimSeat` never reads `request.DisplayName`; the seat keeps the name restored from the snapshot. The XML doc says it is "Name the claiming device shows for the seat." Either honour it (through `NormalizeText`) or remove it from the contract.

#### L6. Room-code comparison is not constant-time
**File:** `Restore.cs:406-412`
`RequireJoinCode` uses `string.Equals(..., StringComparison.OrdinalIgnoreCase)`. Impractical to exploit remotely against a 15-bit secret, but it is the one credential comparison in the codebase that does not use `FixedTimeEquals` — worth aligning for consistency if M2 raises the code's entropy.

#### L7. Room-code trimming is inconsistent between lookup and join
**File:** `InMemoryMatchService.cs:260` vs `Restore.cs:456`
`JoinMatch` does `_joinCodes.TryGetValue(request.JoinCode, ...)` with no `Trim()`; `FindMatchByCode` does `joinCode.Trim()`. A pasted code with a leading space resolves via lookup but fails to join.

#### L8. Token placement is inconsistent
Three routes read `X-Participant-Token` from the header (snapshot, ready, advance-turn); every other authenticated route takes `ParticipantToken` in the request body. Body-borne secrets are more likely to end up in request logs, APM traces and devtools history than a header is. Pick one — the header — and migrate.

#### L9. `MatchHub.LeaveMatchGroup` takes an unvalidated group name
**File:** `Hubs/MatchHub.cs:27-34`
`Groups.RemoveFromGroupAsync(Context.ConnectionId, matchId)` with no parse and no membership check. It can only affect the caller's own connection so the impact is nil, but it accepts arbitrary strings as group names — worth a `Guid.TryParse` for symmetry with `JoinMatchGroup`.

#### L10. Hub methods are not rate-limited
`JoinMatchGroup` (`MatchHub.cs:13`) calls `IsMatchParticipant`, which takes the global `_gate`. A websocket client can invoke it in a tight loop, bypassing the HTTP rate limiter entirely and contending the lock. Token brute-force is infeasible (256 bits), so this is lock contention rather than a credential risk.

#### L11. `.dockerignore` does not exclude database files
`.dockerignore` covers `bin/`, `obj/`, `node_modules/`, `dist/`, `.git/`, `output/`, `.env` — but not `*.db`, `*.db-wal`, `*.db-shm`. `Dockerfile:3` is `COPY . .`, so a local match database sitting in the repo root would be baked into the build layer.

#### L12. Two-phase read in the seat-claim endpoint
**File:** `Program.cs:345-346`
`matches.ClaimSeat(...)` then `matches.GetSnapshot(matchId)` are two separate lock acquisitions. Only `MatchId` and `Version` are broadcast, so nothing is torn in practice — but it is the one place in the API that reads state outside the mutation that produced it.

## 3. Verified sound (explicitly not findings)

These were checked and are correct — worth recording so a follow-up implementer does not "fix" them.

- **Full Thrust authorization is thorough.** Every mutating route resolves a token; every entity-addressed route re-checks ownership via `FindOwnedShip`/`FindOwnedOrdnanceMarker`; owner-only actions (table, rules profile, points limit, advance turn) all check `Role`. Firing additionally checks the turn holder (`Combat.cs:209`, `Firing.cs:275-279`).
- **Token generation and comparison.** 256-bit CSPRNG (`State.cs:195`), compared with `CryptographicOperations.FixedTimeEquals` (`InMemoryMatchService.cs:1644`). Commitment verification likewise (`MovementContracts.cs:103`).
- **No token leakage.** `ToSnapshot` (`Snapshot.cs:16-129`) projects `ParticipantDto` without `Token`, omits commitment hashes and salts, and exposes `RevealedOrders` only for commitments where `IsRevealed && RevealedOrder is not null` (`:81-83`). Persistence deliberately keeps tokens (`Persistence.cs:104-105`) but that file never reaches the wire.
- **Restore ceilings are enforced before allocation.** `Restore.cs:38-47` runs every `RequireWithin` check before the `lock` and before any state is built.
- **SQL injection.** All values are parameterized (`SqliteMatchStore.cs:91-93, 105`); the only interpolated fragment is the table name, guarded by `SafeIdentifier` (`:154-167`) which enforces ASCII alphanumeric + underscore, ≤64 chars, not starting with a digit.
- **Movement arithmetic is bounded.** `MaxVelocityDelta = 100` and `MaxTurnManeuvers = 32` (`FullThrustLightCinematicRules.cs:18, 25`) are checked first in `Validate` (`:106-114`), and `NormalizeManeuvers` independently `.Take(MaxTurnManeuvers)` on the reveal path before the hash is verified (`:256`) — correctly reasoned in the comment at `:253-255`. `Math.Abs(int.MinValue)` is called out explicitly at `:14-16`.
- **Restore body is double-bounded.** `Content-Length` checked (`Program.cs:260`) *and* the stream wrapped in `BoundedStream` (`:271`, class at `:940-982`), with the comment correctly noting Content-Length is a claim not a fact. `MaxDepth = 32` caps parser recursion (`:143`).
- **CORS.** Development reflection is restricted to loopback / RFC1918 / link-local / ULA / `.local` origins via `IsLocalNetworkOrigin` (`Program.cs:875-916`); production refuses to start without configured origins (`:814`). `AllowCredentials` with reflection is correctly scoped.
- **Security headers.** `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (`Program.cs:185-194`).
- **Response-started guard.** The exception middleware correctly rethrows when `context.Response.HasStarted` (`:169-172`) instead of throwing a second exception over the first.
- **Feature flags fail closed.** `bool.TryParse(...) && parsed` (`FeatureFlags.cs:67`) — blank, missing or unparseable leaves an engine off.
- **Log trimming and sequence numbering.** `TrimLog` drops oldest past 4000 (`State.cs:132-138`) and `_nextLogSequence` is kept separately so trimming cannot make two events share a number (`:107-125`).
- **Reveal-failure exploit is already closed.** The `isFailedRevealRepair` logic (`InMemoryMatchService.cs:1314-1324`) and the drop-the-order path (`:1389-1410`) prevent a player from deliberately failing a reveal to read opponents' orders and then re-plotting. Well reasoned in the comments.
- **Docker.** Runs as `$APP_UID` (non-root), multi-stage, no secrets in layers.
