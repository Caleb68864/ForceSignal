## How the app is structured

- **`src/main.tsx` (1927 lines)** is one `App()` component holding all Full Thrust state:
  `session`, `snapshot`, `drafts`, `firingDrafts`, plus ~20 UI-state hooks. It ends with
  `createRoot(document.getElementById('app')!).render(<App />)` at `main.tsx:1927` — no provider,
  no boundary.
- **Screen switching** is three independent flags, not a router:
  - `gameMode` (`'fullthrust' | 'stargrunt' | 'dirtside'`, `main.tsx:69`) picks the game.
  - Inside Full Thrust, a chain of ternaries at `main.tsx:1210-1260` picks
    seat-picker / auth screen / workspace.
  - `activeView` (`'ships' | 'map' | 'log'`, `main.tsx:63`) picks the tab within the workspace.
  - No URL state at all — refresh always lands on Ships, and a Dirtside/StarGrunt game is
    unreachable after reload.
- **API base URL**: `apiBaseUrl = import.meta.env.VITE_API_BASE_URL ?? 'http://localhost:5225'`
  (`lib/api.ts:6`), baked at build time. `Dockerfile:4` sets
  `ARG VITE_API_BASE_URL=http://localhost:8080`.
- **Snapshot flow is the strongest part of the app.** Every mutation returns a `MatchSnapshot`
  and all of them funnel through `applySnapshot()` (`main.tsx:142-155`), which drops any
  snapshot whose `version` is not greater than the last applied (`snapshotVersionRef`) and
  normalizes it via `normalizeMatchSnapshot`. Out-of-order replies cannot regress the board.
- **SignalR**: one connection per `session.matchId`/`participantToken` (`main.tsx:242-304`).
  Custom infinite backoff capped at 30s (`main.tsx:256-259`); `MatchSnapshotChanged` writes to a
  separate `activity` line and triggers a refetch; `onreconnected` re-invokes `JoinMatchGroup`
  **and** refetches independently (`main.tsx:279-285`); connection state renders as text at
  `main.tsx:1158`. Teardown waits for the handshake to settle (`main.tsx:298-303`). This is done
  properly.
- **Storage**: `writeStorage()` (`lib/api.ts:71`) swallows quota errors and returns a boolean;
  drafts (which hold the order-reveal salts) are written first so a filling store sheds the
  snapshot backup rather than the salts (`main.tsx:168-179`).
- **Mutation guard**: `run(work)` (`main.tsx:88-101`) uses a `busyRef` **and** `busy` state so two
  taps in the same frame cannot both dispatch. It is applied inconsistently — see finding 5.

The codebase is well above average. There is real evidence of past bug-hunting in the comments,
`busyRef` re-entrancy guarding, order-preview/firing-solution debouncing, careful normalization of
everything off the wire, and a genuinely thorough responsive CSS pass. The findings below are the
gaps that remain.

## Critical

### 1. No error boundary — any render throw blanks the app mid-match
**`main.tsx:1927`** · Severity: **Critical**

`createRoot(document.getElementById('app')!).render(<App />)` with no `ErrorBoundary` anywhere in
the tree (grep for `componentDidCatch` / `ErrorBoundary`: zero hits). Combined with finding 2 this
is reachable, not theoretical. Losing the screen loses nothing persisted, but a player mid-turn has
no path back except reload.

*Fix:* wrap `<App />` in a class `ErrorBoundary` that renders the error plus an
"Export Last Device Backup" button.

### 2. localStorage is parsed but never validated — a drifted `fleet-library` entry crashes the app
**`lib/api.ts:47-59`, `main.tsx:104`, `main.tsx:1461-1472`, `main.tsx:55`** · Severity: **Critical**

`readJson<T>` catches `JSON.parse` failures but blind-casts the result to `T`:

```ts
export function readJson<T>(key: string): T | null {
  const value = localStorage.getItem(key);
  if (!value) { return null; }
  try { return JSON.parse(value) as T; } catch { localStorage.removeItem(key); return null; }
}
```

`main.tsx:104` does `readJson<SavedFleet[]>(fleetLibraryKey) ?? []`; `main.tsx:1461` reads
`.length`, and `main.tsx:1464-1472` calls `.map()` and `entry.fleet.ships.length`. A stored
non-array, or an entry written by an older `FleetExport` shape, throws during render — and with no
error boundary the whole app goes white. `readJson(sessionKey)` (`main.tsx:55`) is equally
unvalidated: a stale `Session` missing `matchId` produces `GET /api/matches/undefined/snapshot`.

Note the asymmetry: everything off the *wire* is defended (`lib/normalize.ts` takes `unknown`
throughout, by explicit design), but everything out of *localStorage* is trusted.

*Fix:* run library and session through validators using the same `normalize.ts` `unknown`-in
pattern, and drop entries that fail.

### 3. Session write is the one unguarded `localStorage.setItem` left
**`main.tsx:247`** · Severity: **Critical**

```ts
localStorage.setItem(sessionKey, JSON.stringify(session));
```

Inside an effect, not via `writeStorage`. This is precisely the failure mode `writeStorage`'s own
doc comment (`lib/api.ts:60-70`) says it exists to prevent — "the throw escapes the effect, and the
player loses the whole screen mid-game". Every other write in the app was converted; this one was
missed.

*Fix:* `writeStorage(sessionKey, session)`.

### 4. Damage +/- buttons lose clicks and can double-apply
**`components/ShipCard.tsx:729-730`, called from `main.tsx:1770-1801`** · Severity: **Critical**

```tsx
<button type="button" onClick={() => onChange(Math.max(0, value - 1))}>-</button>
<button type="button" onClick={() => onChange(Math.min(max, value + 1))}>+</button>
```

Each click POSTs `updateDamage(ship, { hullDamage: value ± 1 })` where `value` comes from the
*server's* ship. Three fast taps on `+` all read the same pre-update `value` and send `value+1`
three times — the hull rises by 1, and the player believes they recorded 3. The `run()`/`busyRef`
guard is not applied: `main.tsx:1770-1801` calls `updateDamage(...).catch(showError(setMessage))`
directly, so nothing is disabled while a write is in flight.

The same shape applies to the quick damage buttons at `main.tsx:1798-1801`
("Firecon Hit", "Drive Hit", "Weapon Hit"), which all read `ship.<x>Damage + 1`.

*Fix:* route these through `run()`, or hold a local pending delta and reconcile on snapshot.

### 5. Map-side mutations bypass the `busy` guard entirely
**`main.tsx:1869-1871`, `PlayMap.tsx:1487`, `:1489`, `:1247`, `:1270-1272`, `:1097-1100`** ·
Severity: **Critical**

`main.tsx:1869-1871` passes `fireWeapon`, `moveFighterGroup` and `ceaseFire` to `PlayMap` raw:

```tsx
onFire={(ship, draft) => fireWeapon(ship, draft)}
onFlyFighters={(ship, x, y) => moveFighterGroup(ship, x, y)}
onCeaseFire={(ship) => ceaseFire(ship)}
```

`PlayMap.tsx:1487` renders `<button type="button" disabled={!canFire} onClick={onFire}>Fire</button>`
— `canFire` is computed from a snapshot that has not returned yet, so a double-tap fires the same
weapon twice. Same at `PlayMap.tsx:1489` (Done Firing / Hold Fire), `PlayMap.tsx:1247`
(Launch Marker), `PlayMap.tsx:1270-1272` (ordnance Tick / Resolve / Remove), and
`PlayMap.tsx:1097-1100` (fighter Launch / Return / Spend Turn / Recover).

The ship-card Fire button **is** guarded (`main.tsx:1751`: `onFire={() => run(() => fireWeapon(ship, firingDraft))}`).
This is the same control, unguarded, on the other screen. The code comment at `main.tsx:78-81`
describes exactly this bug as having been fixed.

*Fix:* pass `busy` into `PlayMap` and wrap these callbacks in `run()` the way `main.tsx:1751` does.

## High

### 6. Fighter-ops number fields POST on every keystroke
**`PlayMap.tsx:1087`, `:1091`, `:1095`** · Severity: **High**

```tsx
<input type="number" min="0" max={ship.fighterEnduranceMax || 24}
       value={ship.fighterEnduranceUsed}
       onChange={(event) => onChange({ fighterEnduranceUsed: Number(event.target.value) })} />
```

`onChange` here is `onFighterOps`, a network mutation (`main.tsx:1863` →
`POST /api/ships/{id}/fighter-ops`). Editing "Used" from 2 to 14 fires a POST per digit, each
rendering the server's echoed value back into the field mid-typing, and clearing the box sends `0`.

*Fix:* local draft state committed on blur — or reuse the debounce pattern already written in
`lib/useOrderPreview.ts`.

### 7. `response.json()` is unguarded in three places, and a JSON error body destroys the status code
**`lib/api.ts:20`, `:35`, `:44`** · Severity: **High**

`lib/api.ts:20` and `:35` return `response.json()` on the success path with no guard — a 200 with an
empty body throws `SyntaxError: Unexpected end of JSON input`, shown verbatim to the player.

Worse, `lib/api.ts:44`:

```ts
const problem = await response.json() as { title?: string; detail?: string };
return new ApiRequestError(problem.detail ?? problem.title ?? fallback, response.status);
```

A malformed `application/problem+json` body throws a `SyntaxError` **instead of** returning an
`ApiRequestError`. `handleSessionError` (`main.tsx:1134-1142`) then never sees `status === 404`, so
the expired-session recovery (`clearSession()` + "Match session expired") silently does not run —
the player is left with a dead session and a `SyntaxError` on screen.

*Fix:* `try { … } catch { return new ApiRequestError(fallback, response.status); }`, and guard the
success-path parses too.

### 8. Network failures surface as raw browser strings
**`lib/api.ts:107-110`** · Severity: **High**

```ts
export function showError(setMessage: (message: string) => void) {
  return (error: unknown) => {
    setMessage(error instanceof Error ? error.message : 'Something went wrong.');
  };
}
```

With the API down, every action reads "Failed to fetch" — no mention of the server, no retry, no
guidance. For a self-hosted LAN setup this is the single most likely error a user will ever see.

*Fix:* map `TypeError` / `error.name === 'TypeError'` to "Could not reach the ForceSignal server.
Check the host is running and this device is on the same network."

### 9. No request timeout anywhere
**`lib/api.ts:12-36`** · Severity: **High**

Neither `get` nor `post` passes a signal. A hung socket leaves `busyRef.current === true`
(`main.tsx:93`) with the `finally` at `main.tsx:97-100` never running, so **every** guarded button
in the app stays disabled until reload.

*Fix:* `signal: AbortSignal.timeout(15_000)` on both `fetch` calls.

### 10. `tsconfig.json` has no `"strict"`
**`tsconfig.json`** · Severity: **High**

The config sets `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch` — but omits
`strict`, so `strictNullChecks` and `noImplicitAny` are **off** across a codebase whose defining
feature is `?.` and `??` on optional snapshot fields. None of the null handling in `main.tsx` or
`PlayMap.tsx` is actually verified by the compiler. Findings 2 and 12 are the kind of thing `strict`
catches.

*Fix:* `"strict": true` (and consider `noUncheckedIndexedAccess`), then fix the fallout.

### 11. There is no linter, and the code carries lint directives that do nothing
**project root; `PlayMap.tsx:269`, `lib/useFiringSolution.ts:80`** · Severity: **High**

No `eslint.config.*` or `.eslintrc*` exists anywhere in `src/ForceSignal.Web`, yet two files carry
`// eslint-disable-next-line react-hooks/exhaustive-deps`. Nothing enforces hook deps; nothing runs
in `npm test` but `vitest run` (`package.json`) — no typecheck, no lint. `npm run build` is the only
thing that runs `tsc`.

*Fix:* add `eslint` with `eslint-plugin-react-hooks`, and make
`"test": "tsc --noEmit && eslint . && vitest run"`.

## Medium

### 12. Number inputs coerce empty to 0 and POST it
**`main.tsx:1276`, `:1280`, `:1659`, `:1672`; `PlayMap.tsx:1484`; `ShipCard.tsx:133-288`** ·
Severity: **Medium**

`main.tsx:1276` / `:1280` (table width/depth) do `Number(event.target.value)`; clearing the box
yields `0`, and `updateTable` (`main.tsx:1032`) posts a 0-inch table. Same shape at `main.tsx:1659`
(velocity delta), `main.tsx:1672` (turn steps), `PlayMap.tsx:1484` (firing range, `min="1"` not
enforced), and every numeric field in `ShipCard.tsx:133-288`.

`min`/`max` attributes are decoration — nothing validates on submit. `updatePointsLimit`
(`main.tsx:968`) does clamp correctly and is the model to copy:
`Math.max(0, Math.min(99999, Math.round(Number(pointsLimitForm) || 0)))`.

*Fix:* clamp on change everywhere, as `updatePointsLimit` already does.

### 13. The room code has no copy affordance and no explanation
**`main.tsx:1265`, `main.tsx:1232-1243`** · Severity: **Medium**

`main.tsx:1265` renders the code as a bare `<h2>{snapshot?.joinCode ?? session.joinCode}</h2>`.
`main.tsx:1240` asks for "Room code" with no hint about what it is, where the other player gets it,
or that one player creates and the other joins. Nothing in the app touches the clipboard (grep for
`clipboard` / `navigator.share`: zero hits). Two people at a table have to read six characters
aloud.

*Fix:* a "Copy code" button beside the `<h2>`, and one line of helper text on the auth screen —
"One player creates a match and reads out the room code; the other joins with it."

### 14. Display name is never persisted
**`main.tsx:53`** · Severity: **Medium**

`const [displayName, setDisplayName] = useState('Admiral');` — every visit starts as "Admiral",
even though the app already writes four other keys to localStorage
(`constants.ts:14-17`).

*Fix:* seed from a new `forcesignal.display-name` key and write it on change.

### 15. Dirtside's `run()` lacks the re-entrancy ref that `main.tsx` documents as necessary
**`components/ground/DirtsideView.tsx:56-67`** · Severity: **Medium**

```ts
async function run(action: () => Promise<DirtsideSnapshot>, note?: string) {
  setBusy(true);
  try { … } finally { setBusy(false); }
}
```

Guards only with `setBusy(true)`. Two clicks in the same frame both read `busy === false` and both
dispatch, because `disabled={busy}` only takes effect after a re-render. `main.tsx:82-101` uses a
`busyRef` for exactly this reason, with a comment explaining why state alone is insufficient.
`StarGruntView.tsx:60` has the same weaker pattern.

*Fix:* mirror the `busyRef` pattern in both ground views.

### 16. Dirtside re-implements `newId` with `Math.random`
**`DirtsideView.tsx:9`** · Severity: **Medium**

```ts
const newId = () => Math.random().toString(36).slice(2, 10);
```

`lib/api.ts:94` exports a `newId()` written specifically to work in insecure (plain-HTTP LAN)
contexts, with a long comment about why. `StarGruntView.tsx:13` imports the shared one; only
Dirtside diverges, producing 8-char `Math.random` ids for platoon and element keys.

*Fix:* `import { newId } from '../../lib/api.ts';` and delete the local one.

### 17. A Dirtside or StarGrunt game is unrecoverable after a refresh
**`DirtsideView.tsx:23`; `StarGruntView.tsx:58`** · Severity: **Medium**

`const [game, setGame] = useState<string | null>(null);` — the game id lives only in component
state. `dirtsideApi.readGame()` (`lib/dirtsideApi.ts:18`) and `starGruntApi.readGame()`
(`lib/starGruntApi.ts:23`) exist for exactly this purpose and are never called on mount. A refresh,
a tab crash, or toggling back to Full Thrust and returning loses the whole game with no warning.

*Fix:* persist the game id to localStorage and `readGame` on mount.

### 18. Dirtside's error/status line is invisible to screen readers
**`DirtsideView.tsx:96`, `:119`** · Severity: **Medium**

`<p className="constraint-line">{message}</p>` — no `aria-live`, no `role="alert"`. This is the only
place errors from `run()`'s catch (`DirtsideView.tsx:62-64`) are shown.
`main.tsx:1353-1358` gets this right (`aria-live="polite"` on the message, `role="alert"` on the
storage warning).

*Fix:* `aria-live="polite"` on both, `role="alert"` for errors.

### 19. Damage `-`/`+` buttons have no accessible name
**`ShipCard.tsx:729-730`, `ShipCard.tsx:700-702`** · Severity: **Medium**

Both render literal `-` / `+` text with no `aria-label`; the row's meaning lives in a sibling
`DamageMeter` (`ShipCard.tsx:727`) with no programmatic association. A screen reader hears ten
identical "minus" buttons on a ship card. `PlayMap.tsx:381` / `:391` label their zoom buttons
correctly (`aria-label="Zoom out"`), so the pattern already exists in the codebase.

*Fix:* `aria-label={`Reduce ${label} damage`}` / `aria-label={`Add ${label} damage`}`, and the same
for the repair-party steppers using `job.label`.

### 20. The map is unusable without a pointer
**`PlayMap.tsx:410`, `:414-438`, `:439`, `:487`, `:678-746`, `:233-252`, `:963`** ·
Severity: **Medium**

`PlayMap.tsx:410` sets `role="application"` and handles arrow keys for pan and `+`/`-`/`Home` for
zoom (`:414-438`) — good. But plotting a course requires right-click (`:439`), long-press (`:487`),
or a marker drag (`:678-746`); targeting requires right-click or long-press (`:233-252`). There is
no keyboard route to either. `PlayMap.tsx:765-770` deliberately handles Enter/Space on a marker but
only to *select* it. `MapContactCard` is `aria-hidden="true"` (`:963`), so its readout is
unavailable too.

The ship-card Helm tab (`main.tsx:1626-1737`) is the only accessible plotting path, so the app is
not unusable — but the map's own actions are pointer-only.

*Fix:* Enter on a focused enemy marker sets it as target; add a "plot to selected bearing" control
in the helm inspector panel (`PlayMap.tsx:837-843`).

### 21. `mapNotice` fires on every hover
**`PlayMap.tsx:368`, `:673-676`** · Severity: **Medium**

`PlayMap.tsx:368` is `<p aria-live="polite">{mapNotice}</p>`, and `PlayMap.tsx:673-676` rewrites
`mapNotice` on `onPointerEnter` for every marker the pointer crosses. A screen-reader user with a
mouse present gets continuous narration of ship stats they did not ask for.

*Fix:* keep the live region for deliberate actions only; move hover readouts to a non-live element.

## What is already good (do not "fix" these)

- `applySnapshot` version gating (`main.tsx:142-155`) — correct and load-bearing.
- SignalR reconnect: infinite capped backoff, group rejoin, independent resync, visible link state
  (`main.tsx:250-304`, `:1158`).
- `writeStorage` quota handling and the drafts-before-backup write ordering (`main.tsx:168-203`).
- Salt preservation across phase changes (`main.tsx:217-240`) — the comment explains a real,
  subtle data-loss bug that was fixed correctly.
- `useOrderPreview` / `useFiringSolution` debounce + ref pattern (`lib/useOrderPreview.ts`,
  `lib/useFiringSolution.ts`) — textbook; avoids refiring on parent renders and cancels correctly.
- `normalize.ts` / `fleetIo.ts` `unknown`-in coercion for all wire and file data.
- `ShipEditor` drift detection (`ShipCard.tsx:341-358`) — catches lost updates and warns before
  overwriting.
- Long-press timer cleanup on unmount (`PlayMap.tsx:265-270`).
- `newId()` insecure-context fallback (`lib/api.ts:94-106`).
- Confirmations on the two destructive controls (`main.tsx:1331` Leave Session, `main.tsx:1810`
  Destroy).
- CSS: `:focus-visible` outlines on all controls (`style.css:84-88`), breakpoints at 920/760/460px,
  a `@media (pointer: coarse)` block, explicit 44-48px touch targets, and a print stylesheet
  (`style.css:1731`). No animations, so no `prefers-reduced-motion` need. Status is never
  colour-only — `.link-state` carries text ("Link live" / "Reconnecting" / "Link lost").
